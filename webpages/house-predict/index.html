MACHINE LEARNING / MLOPS

House price prediction, built beyond the notebook.

A production-style machine learning system designed to demonstrate how a model moves from training and validation through automated deployment and API-based inference.

THE PROJECT

From model to system.

The goal is not simply to produce an accurate prediction. The project demonstrates the engineering required to make the model reproducible, testable and deployable.

01 / PROBLEM

House price prediction

Train a machine learning model capable of estimating house prices from property characteristics.

02 / DATA

Structured features

Property data is transformed into model-ready features before being passed through the training pipeline.

03 / ENGINEERING

Automated workflow

Training, validation, registration and deployment are connected through an automated CI/CD workflow.

04 / INFERENCE

API predictions

The trained model is packaged with BentoML and exposed through an inference API used by the prediction interface.

MLOPS WORKFLOW

What happens when code changes?

01

Code is pushed to GitHub

Changes to the development branch trigger the continuous integration workflow.

02

The model is trained

The CI workflow executes the training pipeline, producing a new model candidate from the available feature data.

03

The candidate is validated

Automated validation checks are executed before the model is allowed to progress through the pipeline.

04

The model is registered

A validated model is registered so that the deployed artifact can be associated with a specific model version.

05

Airflow orchestrates the lifecycle

Scheduled Airflow workflows update data and features, run monitoring checks and can initiate retraining when drift is detected.

06

CD packages the service

The deployment workflow packages the model-serving application and builds its container image.

07

The image is pushed to ECR

The container image is published to Amazon ECR, providing a versioned deployment artifact.

08

Kubernetes runs the service

The deployment artifact is run as a Kubernetes workload, allowing the serving layer to be managed independently from the CI/CD runner.

09

The model becomes an API

BentoML exposes the packaged model as an inference service that can receive property data and return predictions.

ENGINEERING DECISIONS

Why the system is built this way.

The architecture was designed around reproducibility, separation of concerns and a clear path from experimentation to deployment.

01

Why GitHub Actions?

The training and deployment workflows are triggered automatically rather than relying on manual execution. This makes the pipeline reproducible and ensures that changes to the project can be validated consistently.

02

Why MLflow?

Training code and model artifacts need to be separated from the code used to produce them. MLflow provides a mechanism for tracking experiments and associating model artifacts with their training runs.

03

Why a feature store?

Feast provides a defined feature retrieval layer rather than allowing training code to depend directly on ad-hoc feature preparation. This creates a clearer boundary between data preparation and model training.

04

Why BentoML?

The model should not remain tied to the training environment. BentoML packages the model-serving logic into an explicit inference service that can be containerized and deployed independently.

05

Why Docker and ECR?

The deployment artifact needs to be reproducible and portable. Docker packages the serving environment, while Amazon ECR provides a central registry for the resulting container images.

06

Why Airflow?

CI/CD should not be responsible for scheduled production workflows. Airflow provides a separate orchestration layer for data updates, feature workflows, drift monitoring and retraining decisions.

07

Why Kubernetes?

The serving layer needs to run independently of the CI/CD runner. Kubernetes manages the deployed BentoML workload, including pods, health checks and rollout behaviour, while the container image remains versioned in Amazon ECR.
